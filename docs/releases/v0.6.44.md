# v0.6.44 — Private Communications Hub

The Inbox navigation becomes **Communications Hub**. A new **My Communications** area stores incoming messages separately from the tenant workspace snapshot. Each user can link their Discord identity, connect their own Gmail account, choose Gmail labels to import, review messages, archive them, and create a project task from a message. Existing shared inquiries remain in a clearly labeled section below the private Hub.

## Privacy and task assignment

- New communication rows carry both tenant and owner IDs. The browser never queries the table directly: it has RLS enabled, public/anon/authenticated grants revoked, and the authenticated server filters every read and update by both IDs. Tenant administrators do not receive another user's private messages.
- The Gmail refresh token is encrypted with the existing master key and bound to the tenant and user ID. The token is never returned by the API.
- Creating a task requires an active client, project, and assignee. The server creates the task using only the title and description entered in the task form. The original communication ID, sender, email body, conversation, and attachments are not copied. The source link remains in the owner's private row.
- A Discord message mentioning two linked users makes two independently owned private copies. A bot DM goes to the linked Discord sender. Personal user-to-user DMs remain inaccessible to the bot.
- Historical Discord inquiries had no owner field and were stored in the shared tenant snapshot. They are quarantined from workspace reads and the legacy sync endpoint. They are not silently assigned to a user. Plan a separate reviewed migration if those historical records need to be recovered.

## Installation

1. Back up the existing project and Supabase database. Apply `database/migrations/schema-v12-communications.sql` after v11 in Supabase SQL Editor. The code update does not run SQL automatically.
2. Apply the patch to **v0.6.43**:

```powershell
npm run patch -- "E:\Playwright\ba-client-ops-patch-v0.6.44-communications-hub.zip"
npm run build
npm run typecheck:server
npm run patch:status
```

3. Restart locally or deploy the updated source to Render. Open Communications Hub → My integration settings. Enter each user's numeric Discord user ID, then save. The existing tenant bot token stays in its existing account integration configuration. The bot must have access to the channel and Message Content intent. To receive a bot DM privately, the sender must link their Discord ID.
4. Gmail: create a Google OAuth Web application, enable Gmail API, and register the exact callback shown in My integration settings, such as `https://your-app.example/api/communications/gmail/callback`. Add `GMAIL_OAUTH_CLIENT_ID` and `GMAIL_OAUTH_CLIENT_SECRET` to the **server** environment, retain `TENANT_INTEGRATION_MASTER_KEY`, and restart. Each user then selects **Connect Gmail**, authorizes read access, refreshes labels, chooses POS Registration/Sales Transfer or other labels, saves settings, and selects **Sync selected labels**.

Gmail uses `gmail.readonly` and `userinfo.email`. Google's `gmail.readonly` scope is restricted, and the operator must complete the relevant OAuth verification/security requirements before broad production use. See [Google's scope guide](https://developers.google.com/workspace/gmail/api/auth/scopes).

## Current limits

- Gmail import is user initiated and fetches the latest 30 messages per selected label per sync. It deduplicates by Gmail message ID. This release does not configure Gmail push/watch, historical pagination, reply/send, or automatic background sync.
- The Hub displays plain text and attachment **names**; it does not download or share attachment bytes. HTML-only messages show Gmail's snippet. Conversations with the same Gmail thread ID appear together in the detail view.
- A Discord server mention must include a linked iRipple user. A bot-only mention without a linked recipient has no private destination and is not imported. Discord channel mapping and provider connection status remain separate from the personal ID link.
- The shared inquiry workflow remains available for records explicitly created there. New Discord captures are private communication records, not automatic shared inquiries. Requirements and shared communication log conversion are future additions.
- The app's current project model is tenant-wide; task assignment follows its existing module and workspace permissions. Per-project membership is not introduced by this release.

## Verification

Frontend production build and server TypeScript check pass. Focused API tests verify that a second user and a tenant administrator cannot read another user's private records through the Hub routes; an attempted cross-user status change and task conversion fail; a shared task omits the private sender and full message; and two linked Discord recipients get separate records. No live Google, Discord, Render, or Supabase connection was available for end-to-end verification.
