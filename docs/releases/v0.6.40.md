# v0.6.40 — Requirements & Traceability

Adds a native RTM module to BA Client Ops Tracker, based on v0.6.39.

## Upgrade from v0.6.39

1. Stop the local app and keep your normal source/database backup. Confirm `npm run patch:status` reports 0.6.39.
2. Save the patch ZIP in `E:\Playwright` and run this command from `E:\Playwright\ba-client-ops-tracker`:

```powershell
npm run patch -- "E:\Playwright\ba-client-ops-patch-v0.6.40-requirements-traceability.zip"
npm run build
npm run patch:status
```

3. Start the local app with `npm run dev`, or commit/push the updated source through your existing Render deployment process. Use `npm start` for production after building.
4. In **Internal Admin → Accounts → select the account → Enabled modules**, enable **Requirements & Traceability**. Existing account module assignments are preserved, so this step is needed for existing tenants.
5. In **Users & Permissions**, grant Contributors/Viewers the module as needed. Administrators inherit enabled tenant modules. Contributors also need **Tasks** to add or remove task links. Sign out/in after access changes and refresh old browser tabs.

No new dependencies, environment variables or Supabase SQL migration are required for this upgrade. Existing migrations through your v0.6.39 setup must already be applied. RTMs and their history are stored inside the existing per-tenant `tenant_state.data` JSON snapshot, through the same atomic save function as task data. They do not appear as a separate normalized RTM table. Browser cache remains tenant-scoped as before.

The full-build ZIP is a source release, including the existing templates and assets. For a fresh source checkout run `npm ci` and `npm run build`. Follow the existing database/environment setup documentation for a new installation. Do not overwrite an existing environment file with the example. The upgrade patch does not touch `.env*`, data or credentials.

## What is included

- A dedicated **Requirements & Traceability** navigation module, with tile/list layouts, search and Client, Project, Status, Owner, Approval and Needs Attention filters.
- Multiple RTMs per client/project; each matrix requires a client, project and name. Shared projects retain separate client RTMs. Matrix client/project cannot be changed after creation.
- Optional enhancement, CRF/contract, version, environment and owner fields; Draft, Active, Completed and Archived lifecycle labels.
- RTM entry points in Client and Project details, and **Document Creation → Create / Import RTM**.
- Permanent requirement IDs, parent/child procedures, collapse/expand, priority, environment and acceptance details.
- Documentation, FSD, Development, Testing, Presentation/UAT and Approval stages. Each has status, reference/ticket/test-case code, GAP number, document URL and section fields.
- Many-to-many requirement/stage links from both the RTM stage editor and Task/Subtask forms. Links must match both the client and project; moving linked work requires unlinking it first.
- Coverage percentages, gap checks, change-impact review and authenticated activity history.
- Administrator overrides with a required reason; automatic status remains visible and can be restored.
- CSV/XLSX import with a preview and validation; Excel/CSV export. Excel includes a separate History sheet. Use the supplied CSV template or a workbook exported by this module. The first worksheet is read. Imports append new requirements and reference fields; they do not import task links or overwrite existing rows. Duplicate requirement codes are rejected. Limits: 5 MB file size, 2,000 requirements per matrix, 500 matrices per workspace.
- Archive/activate matrices without deleting their requirements or task links. Archived matrices remain available through the Status filter. Requirement removal requires unlinking work and removing/reparenting children first.

## How progress is calculated

1. Create a matrix and add/import its requirements.
2. Open a stage such as **Development** and select the relevant tasks/subtasks, or add a link inside a Task/Subtask form.
3. When a linked parent includes subtasks, its direct subtasks become the counted work units. Explicit links to the same child are deduplicated. A parent marked done cannot hide unfinished children; a failed or blocked parent still takes priority. Disable **Include subtasks** if the link represents only the parent task.
4. Failed/Rejected work takes priority, then Blocked/Cancelled, then completion. The existing configured closed task statuses are supported. Merely setting Waiting On to Done does not complete RTM work.
5. **Testing** uses the task's new **QA result** field. Completed tasks without an explicit pass show **Done**. Completed work with passing results across all counted units shows **Passed**. A failure remains visible until retested/cleared; reopening a passed task makes it incomplete again.
6. Unlinked stages use their manual status. Linked stages use automatic progress unless an Administrator explicitly overrides it. Not Applicable is excluded from that stage's coverage denominator; an empty denominator displays a dash.
7. Changing requirement details increments its revision and marks it for impact review. Review the affected references/work in **Change impact**, then choose **Mark impact reviewed**. Completed tasks and approvals are not reset automatically.

RTM lifecycle status is a manual label, independent of stage coverage. Parent/child requirements organize the matrix; each requirement row has its own stages and counts separately in coverage. Task/subtask aggregation is independent of the requirement hierarchy.

Progress updates immediately for changes made in the current browser. Changes from another user are visible when the existing workspace refresh runs (on window focus or the five-minute refresh), or on page reload. This release does not introduce push/WebSocket synchronization.

## Boundaries

Document/ticket references are manual links. Generating an FSD, attaching a BRD or entering a Git/Jira number does not itself change RTM status; use linked workflow tasks or manual stage status. This release does not add AI requirement extraction, document-version comparison, direct Git/Jira synchronization or Google Sheets writeback. No changes to the saved FSD Advanced Mode concept are included.

History uses the authenticated actor and retains the latest 10,000 events per RTM. It is an application activity trail, not an external immutable audit ledger. Excel captures calculated statuses at export time; CSV includes a flat matrix with spreadsheet-formula injection protection.

## Rollback

Use `npm run patch:rollback`, then `npm run build` and restart. Back up RTM data before reverting: older application versions do not understand this module and may discard its fields when saving a workspace. A code rollback does not reverse database/user data changes.
