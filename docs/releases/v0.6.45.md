# v0.6.45 — Account-owned Gmail OAuth

Gmail now follows the same account setup pattern as Google Calendar:

1. **Internal Admin** approves Gmail for a tenant account.
2. An **account Administrator** configures that account's Google OAuth Web client in Settings → Integrations → Gmail.
3. Each user with Communications access authorizes their own Gmail address in Communications Hub → My integration settings.

The account's OAuth Client Secret is encrypted in Supabase with the existing `TENANT_INTEGRATION_MASTER_KEY`. Each user's refresh token remains encrypted separately using that tenant and user identity. No Gmail OAuth Client ID or Client Secret is required in Render. Existing `GMAIL_OAUTH_CLIENT_ID` and `GMAIL_OAUTH_CLIENT_SECRET` variables are ignored by this release and may be removed after the new account setup is working.

## Upgrade from v0.6.44

Back up your database and app. Apply `database/migrations/schema-v13-gmail-accounts.sql` in Supabase SQL Editor **after v12**. Then stop the local app and apply the patch:

```powershell
npm run patch -- "E:\Playwright\ba-client-ops-patch-v0.6.45-account-gmail.zip"
npm run build
npm run typecheck:server
npm run patch:status
```

Restart the app or deploy the updated source to Render. The patch does not execute the SQL migration. Keep `TENANT_INTEGRATION_MASTER_KEY` unchanged; replacing it would prevent previously encrypted integration data from opening.

## Configure a tenant

1. Sign in as `internal_admin`, select the tenant, and enable **Allow Gmail**. The tenant's Communications Hub module must also be enabled.
2. Sign in as that tenant's Administrator. Open **Settings → Integrations → Gmail — account setup**. Copy the displayed callback URL. Enable the Gmail API in a Google Cloud project; create a **Web application** OAuth client with that exact Authorized redirect URI. Configure consent with `gmail.readonly` and `userinfo.email` and add test users if the Google app is in Testing. Upload its Web OAuth JSON or enter its Client ID and Secret, check **Enable Gmail for this account**, and save.
3. Each tenant user opens **Communications Hub → My integration settings → Connect Gmail**, grants read access, refreshes Gmail labels, selects the monitored labels, saves, and syncs. Different tenants can configure separate Google Cloud projects and OAuth clients.

Changing the account OAuth credentials gives them a new revision. Existing users are shown **Reconnect Gmail** and must authorize under the new client. Previously imported messages remain private to their owners.

## Callback correction and security

The Google redirect now uses a short-lived dedicated `SameSite=Lax` cookie and checks the original live server session, tenant, user, and account configuration revision. This permits Google's return navigation while the application's normal session cookie remains `SameSite=Strict`. A callback after logout, account disablement, or a changed OAuth configuration cannot save a connection. Account configuration and live user rights are checked by the server, including when Internal Admin disables Communications or Gmail.

## Current limits

The v0.6.44 Gmail import remains a user-initiated sync of the latest 30 messages per selected label. Gmail push notifications, sending replies, attachment downloads, and Viber are outside this update. Gmail `gmail.readonly` is a restricted Google scope; production use may require Google's OAuth verification and security assessment. See [Google's Gmail scope guidance](https://developers.google.com/workspace/gmail/api/auth/scopes).
